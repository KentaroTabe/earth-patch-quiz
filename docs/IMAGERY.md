# 画像の取得と差し替え

仕様 §4.2 / §5.4 / §5.6 / §12 の実装メモ。

---

## 1. いま使っている取得元

**NASA GIBS の Landsat 年次無雲モザイク**（`config/sources.json` の `gibs-landsat-annual`）。

| | |
| --- | --- |
| レイヤ | `Landsat_WELD_CorrectedReflectance_TrueColor_Global_Annual` |
| 分解能 | 30 m/px |
| 時期 | 年次モザイク（TIME=`2000-12-01`）。**中身は 2000 年前後の画像** |
| ライセンス | 米国政府の著作物。出典表記のうえ自由に使える |
| 認証 | 不要 |

仕様 §5.6 のとおり年次の無雲モザイクを使っているので、単日のシーンを選んで雲を弾く工程は要らない。

### なぜこれを選んだか

仕様 原則1 は「一次配布元の衛星画像のみ。NASA と Copernicus に限る」。認証情報なしで一次配布元から 30m の全球無雲モザイクが取れるのは、いまのところ GIBS だけだった。

検討して見送ったもの。

| 候補 | 見送った理由 |
| --- | --- |
| EOX Sentinel-2 cloudless（10m） | CC BY-NC-SA 4.0 の非商用限定。かつ配布元が EOX（第三者）なので原則1に厳密には反する |
| Copernicus Data Space / Sentinel-2（10m） | 認証情報が要る。取れ次第こちらに移す（`cdse-sentinel2` として枠だけ用意済み） |
| GIBS HLS L30/S30（30m・日次） | 日次なので雲が乗る。仕様 §5.6 が避けたい工程が復活する |
| GIBS MODIS/VIIRS（250m） | 2000 km² の枠でも 179px にしかならない |

**仕様 付録の未確定事項 #1（無雲モザイクの提供元とライセンス）は、GIBS を選ぶことで当面決着させた。** 商用利用の制約が無く、出典表記だけで足りる。

### この取得元の弱点

2000 年前後の画像なので、**それ以降にできた地物は写らない。** 確認済みの例。

- パーム・ジュメイラ（ドバイ、2001年着工）→ 写らない
- 三峡ダムの湛水（2003年〜）→ 写らない

また、次のような場所では画質が実用に足りなかった（§4）。

- 雪氷・塩原 … 白飛びする（ヴァトナヨークトル、ウユニ）
- 湿潤な熱帯 … 走査線状の欠測が出る（マナウス、レンソイス）
- 高緯度の山岳 … 雪と岩の見分けがつかない（エベレスト）

**乾燥地・海岸線・火山はよく写る。**

## 2. 取得のしかた

```bash
npm run fetch:dry                     # 通信せず、叩く URL だけ確認する
npm run fetch                         # まだ無いものだけ取得する
npm run fetch -- --force              # 取り直す
npm run fetch -- --only=richat,fuji   # id を指定する
npm run fetch -- --prune              # 不採用（adopted: false）の画像を消す
npm run fetch -- --upload-only        # 取り直さずに R2 へ上げるだけ
npm run fetch -- --patch-only         # 出題用の枠だけ。選別中は広域が要らない
npm run fetch -- --no-upload          # R2 へ上げずに手元へ置くだけ
npm run fetch -- --write-questions    # 実測値を data/questions.js の image に書き戻す
npm run fetch -- --source=gibs-modis-truecolor   # 取得元を差し替える
```

`data/questions.js` の `answer.lat` / `answer.lon` / `frame.areaKm2` を読んで、WMS の GetMap で1枠を1リクエストで取る。タイルの合成をしないので画像ライブラリが要らない。

**1問につき2枚を取る。**

| キー | 中身 | 使う場所 |
| --- | --- | --- |
| `q/<id>.jpg` | 出題する枠 | 出題画面 |
| `ctx/<id>.jpg` | 一辺が `context.sideScale` 倍の広域 | 結果画面 |

広域は「出した枠がどこに収まっていたか」を見せるためのもの。テストで
「正解発表のときに一回り大きい画像があると納得感が出る」という声があって足した。
サイトは中央に白い枠を重ねて、出題した範囲がどこだったかを示す。位置と大きさは
`1 / sideScale` から計算しているので、画像に焼き込んでいない。

出力は `img/q/` と `img/ctx/`、それに `img/manifest.js`（自動生成・手で編集しない）。

### 枠の大きさと画素数

引き伸ばさない（仕様 §5.4）。30 m/px、出力の上限は 1400px。

| 枠 | 一辺 | 画素数 | 実効の分解能 |
| --- | --- | --- | --- |
| 200 km² | 14.1 km | 471 px | 30 m/px |
| 500 km² | 22.4 km | 745 px | 30 m/px |
| 1000 km² | 31.6 km | 1054 px | 30 m/px |
| 2000 km² | 44.7 km | 1400 px | 32 m/px |
| 5000 km² | 70.7 km | 1400 px | 51 m/px |
| 10000 km² | 100.0 km | 1400 px | 71 m/px |
| 20000 km² | 141.4 km | 1400 px | 101 m/px |

**仕様 §5.4 の表は 2000 km²（一辺45km）までだが、5000〜20000 km² を足してある。** 内陸デルタ・三角州・塩湖のように差し渡し 100km を超える地物は、45km の枠では扇の内側だけが写り、模様にしか見えなかった。枠を広げたら5件が使えるようになった（§4）。

2000 km² を超えると 1400px の上限に当たり、元の 30m より粗くなる。ただし対象がもともと大きいので、見え方に問題は出ていない。

50 km² / 100 km² の枠は 236 / 333 px にしかならず、30m の取得元では実用にならない。**小さい枠を使いたければ 10m の取得元が要る。**

現在の100問の枠の内訳。広域はこの9倍の面積（一辺3倍）になる。

| 枠 | 問数 | 広域 |
| --- | --- | --- |
| 200 km² | 9 | 1,800 km² |
| 500 km² | 15 | 4,500 km² |
| 1000 km² | 7 | 9,000 km² |
| 2000 km² | 26 | 18,000 km² |
| 10000 km² | 16 | 90,000 km² |
| 20000 km² | 27 | 180,000 km² |

広域はすべて 1400px の上限に当たる。いちばん広い 180,000 km²（一辺424km）で
303 m/px まで粗くなるが、位置を掴むための画像なので問題は出ていない。

**広域で1件だけ欠測が乗っている。** `ctx/fuji.jpg` の右端（箱根のあたり）に走査線状の縞が出る。
出題する枠の外側なので採用したが、気になるなら `context.sideScale` を下げるか、
その問だけ別の取得元にする必要がある。

## 3. 目視の手順

仕様 §13 のとおり、機械は「人が見る順番を並べ替える」だけで、採否は人が決める。

```bash
npm run fetch -- --patch-only --no-upload   # 選別中は出題用の枠だけ取る
npm run sheet                               # work/contact-sheet-N.html を書き出す
npm run serve                               # ブラウザで開く
```

100問規模になると HTML の一覧はブラウザの読み込みが間に合わないので、`--montage` で1枚の PNG にまとめて見る。

```bash
npm run score -- --screen                        # 機械の下見（未決定だけ）
npm run sheet -- --only=undecided --montage      # work/montage-N.png
```

見るのは3点。

1. **狙った地物が枠に収まっているか。** 収まっていなければ `frame.areaKm2` か中心座標を直して取り直す。
2. **欠測や白飛びが無いか。** 走査線状の縞、真っ白な面、斑点、色付きの筋。
3. **見たままを一文で言えるか。** 言えないなら `headline` が書けないということなので落とす。

### 機械の下見でどこまで落ちるか

`npm run score -- --screen` は未決定の候補を 700px で見て、白飛び・のっぺり・走査線状の欠測を測る。93件に走らせたところ27件が引っかかったが、**そのうち何件かは誤検出だった。**

| 機械の判定 | 実際 |
| --- | --- |
| 欠測の縞 2% 超 | ほぼ当たり。目視でも落とした |
| 白飛び・黒潰れ | **深い海や湖を欠測と取り違える。** ケープコッド、チチカカ湖は誤検出 |
| 白飛び（雪氷） | 当たり。氷河はほぼこれで落ちる |
| のっぺり | **「広大で特徴が少ない」問題を狙って入れている場合は誤検出。** ルブアルハリ砂漠、テネレ砂漠は意図どおり |

**機械の判定は参考であって、採否ではない。** 27件のうち5件は目視で拾い直した（malaspina、white-sands、cape-cod、titicaca、rub-al-khali）。

彩度で欠測を拾おうとした案は捨てた。砂漠の砂も彩度が高く、区別できなかった。

採否は `data/questions.js` の `adopted` に書く。

- `true` … 採用
- `false` … 不採用。**理由を `reject` に書く**
- 書かない … 未決定

**不採用を消さないこと。** 消すと取得のたびに同じ画像が戻ってくる（仕様 §6.1）。

## 5. Cloudflare R2

画像は R2 に置く。設定は `config/pipeline.json` の `r2`、秘密情報は `.env.local`。

### 設定

**アカウントIDとバケット名、アクセスキーはリポジトリに書かない。** 公開リポジトリなので、`.env.local`（`.gitignore` 済み）から読む。

```bash
cp .env.local.example .env.local
# .env.local を開いて値を入れる
```

```
R2_ACCOUNT_ID=...
R2_BUCKET=...
R2_ACCESS_KEY_ID=...
R2_SECRET_ACCESS_KEY=...
```

API トークンの権限は「オブジェクトの読み書き」で足りる。管理者権限は要らない。

### アップロード

```bash
npm run fetch -- --upload-only   # 手元の画像を取り直さずに上げる
npm run fetch -- --force         # 取り直して上げる
npm run fetch -- --verify-only   # 公開URLから読めるかだけ確かめる
```

S3 互換 API に SigV4 で署名して PUT している（`scripts/lib/r2.mjs`）。外部ライブラリは使っていない。

アップロードのあと、**上げたものが公開URLから実際に読めるかを1件ずつ確かめる。**

```
公開URLの確認 25 件  https://pub-xxxxxxxx.r2.dev/
  25 件すべて読めました
```

読めないものがあれば終了コードが 1 になる。バケットへの書き込みが成功していても、公開設定が入っていなければサイトからは見えない。この確認が無いと、デプロイして初めて画像だけ出ないことに気づく羽目になる。

バケットへの書き込みが成功していても、公開設定が入っていなければサイトからは見えない。この確認が無いと、デプロイして初めて画像だけ出ないことに気づく羽目になる。

### 公開URLはバケットごとに違う

移行のときにここで詰まった。**r2.dev のサブドメインはバケットごとに別々に割り当てられる。** 別バケットの URL を使うと、アップロードは成功しているのに 404 だけが返る。S3 API でバケットの中身を数えれば、書き込みが成功していることはすぐ確かめられる。

公開URLは Cloudflare の **R2 → 該当バケット → 設定 → パブリックアクセス** に表示されているものを使う。

### サイト側

`assets/config.js` の `imageBase` を公開URLに向ける。**触るのはこの1行だけ。**

```js
imageBase: 'https://pub-xxxxxxxx.r2.dev/q/',
```

`img/q/` は `.gitignore` に入れてある（仕様 §4.1）。手元に用意し直すときは `npm run fetch`。

**読めることを確かめる前に Git から外さないこと。** 外した瞬間、どこからも画像が出なくなる。

### 設定の優先順位

`.env.local` は手元の上書き用なので、**`config/pipeline.json` より環境変数が優先される。**

| 値 | 環境変数 | config |
| --- | --- | --- |
| アカウントID | `R2_ACCOUNT_ID` | `r2.accountId` |
| バケット名 | `R2_BUCKET` | `r2.bucket` |
| 公開URL | `R2_PUBLIC_BASE` | `r2.publicBase` |
| アクセスキー | `R2_ACCESS_KEY_ID` / `R2_SECRET_ACCESS_KEY` | （config には置かない） |

公開URLは秘密ではないので `config/pipeline.json` に置いてある。アカウントIDと鍵は `.env.local` だけ。

アカウントIDは `https://` や `.r2.cloudflarestorage.com` が付いていても受け付ける。Cloudflare の画面からは S3 API のエンドポイントごとコピーされることが多いため。

### r2.dev エンドポイントについて

いま使っているのは `pub-….r2.dev` の公開エンドポイント。**仕様 §4.2 はこれを本番で使わないよう明示している。**

> `r2.dev` の公開エンドポイントは検証用で、レート制限があり、超えると 429 が返ります。本番では `img.example.com` のような独自サブドメインを R2 バケットに向けてください。ここを忘れると、人が集まった瞬間に画像だけ表示されなくなります。

五人に触ってもらう段階（仕様 §1）では問題にならないが、**それより広く見せる前にカスタムドメインへ移すこと。** 移行は R2 バケットにカスタムドメインを割り当て、`imageBase` を差し替えるだけ。

## 6. 取得元を足す

`config/sources.json` に1件足すだけ。スクリプトは触らなくてよい。

```json
"あなたのソース名": {
  "label": "表示名",
  "protocol": "wms",
  "endpoint": "https://…",
  "wmsVersion": "1.1.1",
  "srs": "EPSG:4326",
  "layers": { "truecolor": "レイヤ名" },
  "time": "2024-01-01",
  "metersPerPixel": 10,
  "maxRequestPx": 4096,
  "sensor": "s2",
  "credit": "出典表記",
  "license": "…",
  "commercialUse": true,
  "requiresApproval": false,
  "reflectanceLinear": true
}
```

`reflectanceLinear` は弁別性の計算に効く（docs/SCORING.md §2）。表示用に伸張された合成画像しか出さないソースは `false` にする。

`protocol` が `wms` 以外のものは未実装。`cdse-sentinel2`（`sentinel-hub`）は設定だけ置いてある。

**新しいソースを採用する前に、ライセンスを必ず個別に確認すること。** 無雲モザイクは提供元と年次で条件が違う。非商用限定のものを選ぶと将来の選択肢を狭める。

## 7. 使えないもの

**Google マップおよび Google Earth の画面キャプチャは、どんな形でも使わない**（仕様 原則1 / §12）。リンクを張るのは問題ないので、結果画面には Google マップへのリンクを置いている。

`npm run validate` は `credit` に `Google` が入っていたら落とす。
