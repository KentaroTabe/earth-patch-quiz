# 弁別性と知名度

仕様 §5 の実装メモ。式そのものは仕様に書いてあるので、ここには**実際に動かして分かったこと**を残す。

パラメータはすべて `config/pipeline.json` にある。スクリプトに数値を直接書かない。

---

## 1. なぜ二軸なのか

弁別性を「画像の情報量」で定義すると失敗する。熱帯雨林も砂丘もテクスチャの情報量は極めて高いが、どのタイルも同じに見えるのでクイズにならない。必要なのは情報量ではなく **他のどことも違うか**。

さらに、弁別性が高いだけでは足りない。シベリアの無名の湖は地球上で唯一無二だが、誰も答えられない。だから第二の軸として知名度が要る。

| 軸 | 測るもの | 実装 |
| --- | --- | --- |
| 弁別性 `distinct` | 他と違うか | `scripts/lib/image-features.mjs` |
| 知名度 `fame` | 知られているか | `scripts/lookup-fame.mjs` / `scan-candidates.mjs` |

---

## 2. 弁別性の特徴量

| 特徴量 | 実装 | 重み |
| --- | --- | --- |
| 最近傍距離 `nn` | 64次元ハッシュ（4×4セル × R/G/B平均・エッジ密度）での kNN 距離 | 0.45 |
| 水域の分散 `wv` | 4×4に割ったときの水域率のばらつき | 0.25 |
| 色クラスタ数 `c` | k-means(k=6) の有効クラスタ数（占有率 2% 以上） | 0.20 |
| 直線性 `l` | Sobel + Hough 変換の最大投票値を対角長で正規化 | 0.10 |

`norm()` は全候補の中での正規化（5%〜95% 分位で切ってから 0〜1 に伸ばす）。**候補集合が変われば値も変わる**。絶対評価ではない。

### 水域率の判定を2通り持っている理由

仕様 §5.3 は NDWI（緑と近赤外の比）を使うと書いている。実装もそのつもりで書いたが、**NASA GIBS の True Color / Bands743 は表示用に伸張された合成画像**で、画素値が反射率そのものではない。この状態で NDWI を計算すると、

```
richat（サハラ砂漠のど真ん中）  水域 94%
musandam（岩山と海）           水域 100%
```

となり、まるで役に立たなかった。伸張の分だけ緑と近赤外の比が歪む。

そこで取得元に `reflectanceLinear` を持たせ、

- `true`（反射率がそのまま入っている）→ 仕様どおり NDWI
- `false`（表示用の合成画像）→ RGB だけの経験則（青が赤より強く、かつ暗い）

を切り替えるようにした。切り替え後の値は妥当になった。

```
richat 0% ／ dead-sea 22% ／ musandam 52% ／ great-salt-lake 60%
```

**Sentinel-2（`cdse-sentinel2`）を有効にすれば NDWI に戻る。** そちらが本来の実装。

## 3. 重みはまだ調整していない

仕様 §5.3 は「重みは必ず目視でチューニングします」と書いている。**まだやっていない。** 現在の重みは暫定値のまま。

やっていないことがどう出ているか、25問の実測で確かめられる。

| 順位 | id | 弁別性 | 人が見た印象 |
| --- | --- | --- | --- |
| 1 | capetown | 0.975 | 悪くない |
| 2 | musandam | 0.957 | 悪くない |
| … | | | |
| 22 | richat | 0.337 | **25枚のうち最も分かりやすい**のに22位 |
| 24 | fuji | 0.075 | 円すいの山として一目で分かるのに下から2番目 |
| 25 | manicouagan | 0.048 | 輪の形が明快なのに最下位 |

水域の分散が効きすぎて、海が入っている枠が上位に来ている。richat も fuji も manicouagan も水がほとんど無いので沈む。枠を広げて足した5問でも同じ傾向が出ていて、水のある panama（0.582）と danube-delta（0.566）が上位、水の無い etosha（0.421）と lake-eyre（0.388）と okavango（0.376）が下位になった。**人が見た印象とはほぼ無関係。**

**やるべきこと（仕様 §5.3 のとおり）**

1. 候補から100枚を無作為に抜く（`npm run sheet` で一覧を出す）
2. 人が「分かる／分からない」の2値でラベルを付ける
3. `distinct` の順位との相関を見て `config/pipeline.json` の `distinct.weights` を調整する

これをやらずに重みを固定すると、まず間違いなく雨林と農地が上位に来る。今の20問では「海」が上位に来ている。症状は違うが原因は同じ。

## 4. 知名度と難易度

```
fame       = norm(log(1 + 言語版数))
difficulty = 1 + floor(5 * (1 - fame))     // 1〜5、1が易しい
```

`norm()` は §5.3 と同じく**候補集合の中での正規化**。つまり難易度は問題バンクに対する相対値で、**問題を足すと既存の難易度も動く**。`npm run score` を通し直して `data/questions.js` の `scores` を更新すること。

絶対値で正規化する案（`log(1+langs) / log(1+250)` など）も試したが、有名な地物ばかりを選ぶ性質上、難易度1〜2に11問が固まって使いものにならなかった。相対正規化のほうが配分が素直に出る。

### 現在の配分（25問）

| 難易度 | 問数 | id |
| --- | --- | --- |
| 1 | 8 | vesuvio, dead-sea, suez, panama, brasilia, etna, grand-canyon, fuji |
| 2 | 4 | great-salt-lake, lake-eyre, okavango, toba |
| 3 | 6 | musandam, nasser, crater-lake, venezia, danube-delta, richat |
| 4 | 4 | capetown, etosha, betsiboka, manicouagan |
| 5 | 3 | sossusvlei, ngorongoro, lena-delta |

仕様 §5.5 の理想は1セット `1,1,2,2,2,3,3,4,4,5`。2セット分だと `1×4 / 2×6 / 3×4 / 4×4 / 5×2` が要る。難易度2 が4問しかないので、2セット目の一部は近い難易度で埋まる（`assets/app.js` の `bestIndex`）。

20問だった時点では `7 / 6 / 4 / 2 / 1` で難易度1に偏っていた。枠の上限を伸ばして5問（panama, danube-delta, etosha, okavango, lake-eyre）を足したところ、**難易度は相対値なので全体が押し広げられ**、4と5が増えて配分がかなり改善した。この動き方そのものが、難易度が絶対値ではないことの実例になっている。

## 5. 候補点の作り方の注意

仕様 §5.2 のクエリを実装するとき、2つ変えた。

**天体の絞り込みを足した。** `wdt:P625` は月や火星の地物にも付いている。そのままだと火星のカルデラが地球の候補に混ざる。`wikibase:geoGlobe wd:Q2` で地球に限定した。

**`wdt:P31/wdt:P279*` は思ったより広く拾う。** カルデラ（Q39816）だけを指定しても、南極の乾燥谷が1000件以上返ってくる。Wikidata の上位クラスをたどると「窪地」「谷」まで届いてしまうため。今は南極を落とす処理で結果的に消えているが、クラス指定そのものは仕様 付録の未確定事項 #3 のまま。深さを固定する（`P279{0,2}` など）か、クラスを列挙し直すかを決める必要がある。

## 6. 使うコマンド

```bash
npm run scan        # Wikidata から候補点を作る（--class= でクラスを絞れる）
npm run score       # 採用済みの問題を採点する
npm run score -- --write                    # 結果を data/questions.js に書き戻す
npm run score -- --candidates --fit-frame   # 候補を採点し、枠サイズも決める
npm run fame        # 手で選んだ問題の言語版数を測る
npm run sheet       # 目視用の一覧を書き出す
```

問題を1問足したら `npm run score -- --write` を通し直すこと。**難易度は相対値なので、既存の問題の値も動く。** 手で貼り直すと必ず取りこぼす。
